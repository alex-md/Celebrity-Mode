## Build and run

Use JDK 17 and the checked-in Gradle wrapper. Java output targets release 11, matching the [official example plugin](https://github.com/runelite/example-plugin). Development resolves RuneLite `latest.release`; the verified build resolved **1.13.1**.

```sh
./gradlew clean test jar
./gradlew run
```

Use `./gradlew run -PverifyModels` for an opt-in check that builds every gear tier and applies eight animation sequences against the actual client cache at the login screen. This check is confined to the developer launcher.

The developer launcher opens RuneLite with the plugin loaded. Enable **Fame Simulator** in its plugin panel after logging in. The ordinary build artifact is `build/libs/fame-simulator.jar`; the developer launcher is the supported local test route. `./gradlew shadowJar` also builds a developer launcher with dependencies. The plugin is listed in the Plugin Hub as Fame Simulator. Updates use the existing `plugins/celebrity-mode` manifest and require maintainer review through the [Plugin Hub process](https://github.com/runelite/plugin-hub).

There are no additional runtime dependencies, network requests, telemetry, menu actions, or packet hooks in plugin code. Fan PMs use one bounded, disposable background scheduler while active; the rest of the scene simulation runs on client ticks. Build tools and the RuneLite client itself retain their normal dependency/download behavior.

## Sidebar development

The fan club panel uses RuneLite’s [PluginPanel](https://github.com/runelite/runelite/blob/master/runelite-client/src/main/java/net/runelite/client/ui/PluginPanel.java), `NavigationButton`, and `ClientToolbar`. Swing components are created and refreshed on the EDT. Controls write through `ConfigManager`; the existing `ConfigChanged` subscription applies scene mutations on the client thread. Configuration keys remain compatible with the regular settings panel. A quote draft survives unrelated setting changes and external edits; Save replaces the stored pool, and Revert reloads it.

The toolbar icon loads the supplied crown PNG from the bundled classpath resources and scales it for the sidebar. The root `icon.png` is a 48×48 version for Plugin Hub discovery. No external image library is required. Sidebar layout coverage lives in `CelebrityModePanelTest`; review the actual panel through `./gradlew run` for visual changes.

## Fan PM engine

`pm.FanDialogueGenerator` and overhead `chat.FanDialogueGenerator` share `QuickChatComposer` and `UsernameGenerator`. The short-chat grammar composes reactions, greetings, requests, praise, disbelief, jokes, and context comments from lexical slots. Each result carries its unexpanded template in `FanUtterance`, so changing a subject, player name, capitalization, or punctuation does not disguise a repeated sentence structure.

Overhead generation chooses 80% short grammar, 10% single-clause medium grammar, and 10% the original resource corpus. The length bucket stays fixed while selecting alternatives, preventing repetition filtering from biasing the crowd toward long sentences. Recognition and other routine event reactions also stay brief; level reactions retain the actual skill and level. All original overhead patterns and event lines remain available.

PMs choose 75% short grammar, 10% medium grammar, 10% `ClassicFanDialogue`, and 5% longer `ConversationComposer` dialogue. Original PM templates remain available, with hype/friend/request/skeptic weights of 45/25/20/10. PM subjects are fictional fan chatter, not verified loot or achievement observations. Recent PM names retain 128 entries; normalized line memory retains 96 and structure memory 12. Short and medium sentence structure checks span all senders. Repeated classic/long conversation buckets switch to compact alternatives after bounded retries.

Overhead chat remembers 96 crowd lines and 16 per fan, plus 16 crowd structures and six per fan. Wording signatures ignore the player name, case, and punctuation, and normalize common abbreviations. Candidate selection evaluates at most 48 alternatives and scores recent wording, recent structures, personal repeats, and matching structures in other visible long messages. If every candidate is familiar, it chooses the least repetitive rather than searching indefinitely. Custom quotes preserve their existing pool behavior and are not forced through generated-dialogue structure filtering.

`CompanionConversations` adds 144 authored three- to five-turn topics with alternate wording. Six shared subject pools (snacks, drinks, towns, bosses, pets, and chores) are rolled once per exchange so callbacks remain coherent. Topics include friendly debates, keyboard spam replies, deliberate typo corrections, familiar social moments, and longer back-and-forth stories. Topics include social chatter, personality-specific scenes, and activity-specific exchanges. The scheduler holds at most one exchange, reserves two nearby visible speakers and has a one-in-three chance to reserve a third nearby fan for the closing turn, and uses ordinary sender cooldowns and overhead history for every turn. Openings replace a due speaker's ordinary comment; replies wait 5–10 ticks, existing text expiry, and typing cooldowns. A reply expires after 60 ticks. New exchanges are considered after 45–144 ticks; the first has a 30–79 tick warm-up. The last 48 topics are excluded from selection. Participants more than six tiles apart, departures, activity/skill/target/player changes, event reactions, reconfiguration, and scene resets cancel pending replies. Custom-only mode and Off suppress these scenes. Conversation partner tracking is social metadata only and does not change either body orientation. No external dialogue service or player-chat monitoring is used.

`ChatTypingStyle` adds typing slips to generated overhead lines and authored conversation turns, retaining the original structure ID so a misspelling does not disguise a repeated template. Per-line chances are 4% for Quiet, 14% for Memer/Excited, and 9% for other personalities. A single eligible word receives an internal letter transposition, omission, or duplication; player and companion names, observed gear/targets, skill names, and numeric levels remain intact. Custom quotes and level/event details retain their authored wording. Occasional standalone keyboard reactions include `@@@@`, exclamation strings, stretched cheers, and keysmashes: 5% candidate chance for Memer/Excited/Hypeman, 2% for other talkative personalities, and none for Quiet. Each kind has a stable structure ID and passes the existing history scoring; actual selection rates depend on repetition penalties. Punctuation-only signatures retain their punctuation instead of collapsing to an empty string. The short grammar now includes everyday snack/drink/pet/chore/town slots and substantially more casual comments; shared grammar additions also reach PMs, while the new typing-slip and keyboard decorator is specific to overhead chatter.

A sender's ID selects a consistent typing rate of 2–4 characters per game tick (roughly 40–80 words/minute), with additional thinking time. A client-thread map holds an independent speech deadline for each visible fan. First messages are spread over 1–18 ticks in Normal and 1–14 in Spam; Low spreads them over up to 15 ticks per visible fan. After typing cooldown, thinking pauses use a bounded exponential draw with means of four ticks in Normal, two in Spam, and 7.5 ticks per visible fan in Low (minimum five), plus one tick. Existing overhead text expires before ordinary chatter replaces it. There is no shared recurring gate or crowd-sized batch. Departed/invisible fans lose their deadlines; arrivals receive fresh randomized ones, and reconfiguration/reset clears scheduling state. Events allow one immediate reaction and another after 1–5 ticks, storing the already-personalized observed event details. Pending reactions expire if over five ticks late or the player name changes, and reconfiguration/reset discards them. Even Spam respects per-sender typing time. Display duration also grows with message length. Custom-only event behavior is preserved.

Crowd and PM handles combine words, personal names, syllables, separators, and optional numeric suffixes within 12 valid characters. Normalized exclusions prevent player impersonation and duplicate names within the active crowd; bounded retries have a deterministic collision fallback.

`FanMessageScheduler` creates one daemon `ScheduledThreadPoolExecutor` with one outstanding delayed task. Exponential inter-arrival delays target 20/80/180/360 PMs per minute. The worker receives only a character-name snapshot and never calls the client API. Its inbox retains at most 32 messages; overflow is dropped, stale messages expire after five seconds, and dispatch is limited to two messages per client tick and twelve per rolling second. Scheduling is relative to the current worker run, avoiding timer catch-up loops. A generation token invalidates callbacks already racing with cancellation. Disable, loading, hopping, logout, and plugin shutdown clear the owned inbox, cancel the timer, and shut down the executor; login or re-enable creates a fresh session.

`FanPmEngine` runs the client bridge on `ClientTick`. It builds plain `QueuedMessage` values with `PRIVATECHAT`, fictional names, and Jagex-escaped text (so `<3` remains a literal heart). It leaves formatting and timestamp overrides unset. RuneLite's [ChatMessageManager](https://github.com/runelite/runelite/blob/master/runelite-client/src/main/java/net/runelite/client/chat/ChatMessageManager.java) and the native renderer apply the active Chat Color, split-chat, transparency, timestamps, and private-chat filters. No duplicate style settings or custom chat overlay are introduced.

The bridge queues a bounded batch and calls the public manager `process()` immediately on the client thread. Thus this plugin leaves no deferred PM entries in RuneLite's shared queue after a completed dispatch; it never clears another plugin's queue. Existing displayed history is left to native chat/history behavior. `PRIVATECHATOUT` is not used, and no messages are sent to the server. Random badges are omitted because standard configuration does not expose such a toggle.

Optional audio uses the one-argument `Client.playSoundEffect(SoundEffectID.UI_BOOP)`, which follows native sound-effect volume; the volume-forcing overload is not used. Playback is gated to once per two seconds. The client has no dedicated PM sound constant in this API, so this is the native UI notification sound, not a custom audio asset. Other enabled chat-notification plugins retain their own behavior.

Tests use a manual scheduled executor and clock to cover traffic means and variance, bounded queues, stale drops, rolling dispatch caps, cancelled-callback races, fresh sessions, native PM fields/escaping, sound throttling, and config/login/shutdown gating without timing-dependent sleeps. Corpus tests check legal names, text bounds, a mix of playful and ordinary chat, tone weights, and variety.

## Implementation

`CelebrityModePlugin` owns event subscriptions and dispatches configuration/lifecycle mutations to the client thread. `FanManager` owns every fan's single active `RuneLiteObject`, appearance/model, breadcrumb history, scene identity, and chat scheduler. Removing an entity always unregisters its object. Scene resets unregister all objects and clear local interpolation positions before reseeding. Models remain reusable across resets; changing the gear theme discards them.

The public [RuneLiteObject API](https://static.runelite.net/runelite-api/apidocs/net/runelite/api/RuneLiteObject.html) and [AnimationController API](https://static.runelite.net/runelite-api/apidocs/net/runelite/api/AnimationController.html) handle registration and animation. Each fan owns a controller; sequence resources are cached, and unchanged states do not restart animation. Animation IDs use current generated `gameval` names; equipment is discovered from the current cache. Normal, whip, and staff poses use corresponding supported sequences; waves and cheers complete once before returning to idle.

The public API does not expose creation of arbitrary player compositions. `FanModelFactory` uses `Client.getIndexConfig()`, `loadModelData()`, and `mergeModels()` to assemble selectable male identity kits and item **worn** meshes. Its small cache-definition decoder follows the public RuneLite [KitLoader](https://github.com/runelite/runelite/blob/master/cache/src/main/java/net/runelite/cache/definitions/loaders/KitLoader.java) and [ItemLoader](https://github.com/runelite/runelite/blob/master/cache/src/main/java/net/runelite/cache/definitions/loaders/ItemLoader.java) formats, including extended model IDs. It clones mutable mesh data before recoloring, texturing, or translating it. Unsupported equipment definitions fall back to the fan's body kits; temporarily missing model resources retry the same appearance after a short cooldown. The wardrobe indexes wearable cache items incrementally and classifies their names into broad progression and combat-style groups. A body anchors each outfit: matching head/leg families are used when available, and weapons remain within one progression step and a compatible style. Casual or unclassified bodies do not acquire mismatched combat armour. Accessories have an upper progression bound, prestige capes also require an appropriate weapon, novelty props are excluded, and two-handed weapons suppress shields. Modern Gear prefers higher progression gear, also admitting newer unclassified equipment. These are appearance heuristics, not inferred account stats or a price lookup; unfamiliar future names may need rules. There is no fixed list of complete outfits. It never changes a real `Player` or `PlayerComposition` and uses no reflection.

Logical positions are **scene-space WorldPoints within the active WorldView**, obtained from the local player's local position. In an instance, these are deliberately not canonical template coordinates: two copies of the same template room remain distinguishable. World-view identity, ID, base coordinates, plane, loading state, and impossible displacement are checked before using retained local coordinates. Render points are rebuilt with WorldView-aware conversions; the overlay uses RuneLite Perspective projection.

Breadcrumbs contain at most 80 unique movement positions, with collision-validated intermediate tiles for running. Loose Crowd allows more independent lateral choices; Trail keeps a narrower route. Personal space mildly prefers open tiles without requiring unique slots. Each departure samples a 0–4 tick reaction delay and an additional 0–24 client-cycle start offset. Follow clicks refresh every 1–4 ticks, sooner when nearly reached. Catch-up runs begin at individual distances of 3–5 tiles and continue until within one tile. Lateral offsets follow the heading at the fan's delayed route anchor, and a follower ahead of its moving anchor can hold rather than backtrack. On stopping, each fan retains its existing click until its own notice deadline, sampled 2–10 ticks later (Quiet adds three). It then chooses a viewing spot in the configured social radius, with travel cost and local occupancy preferences. Some fans already comfortably inside that radius keep their spot. There is no rule requiring settled fans to remain behind the player. Stops retain their chosen destination until later social decisions or settings changes. Resuming travel starts a new delay leg without discarding routing history.

A deterministic cohort of roughly 60% starts gathering at staggered idle thresholds of 25–74 ticks (15–44 seconds); the others keep their viewing spots. IDs select stable groups of up to four sharing a nearby patch, with individual preferred spots. Each walk targets at most two tiles from the fan and stays within Maximum spread of the player, subject to collision checks; a fan already outside that range can take short corrective steps inward. Ordinary reconsideration pauses are 35–100 ticks; Quiet and Screenshotter personalities pause for 65–150 ticks. Once within two tiles of their group home, fans keep watching on three out of four reconsiderations. A timer provides an opportunity to move rather than requiring a walk. Blocked social destinations are reconsidered after three failed steps. Each fan decides from its own pause and current destination. The old simultaneous-walk quota and one-start-per-tick gate have been removed. Idle members retain the heading of their last movement, even while chatting or emoting. Emotes hold their position. Resuming travel clears idle targets; moving crowds never initiate wandering. Movement remains active when chat and reactions are disabled, and a crowd-wide timer limits stationary emotes.

`WorldArea.canTravelInDirection(WorldView, ...)` handles walls and diagonal corners. Movement first uses the breadcrumb route; blocked direct movement permits a detour of at most 96 visited tiles within six tiles. There is no global per-fan pathfinder. Missing/inactive objects, out-of-scene locations, or separation over 45 tiles can trigger individual repair. A healthy on-scene fan is no longer respawned because it stalled or its destination is more than 24 tiles away. Blocked fans wait and retry; ordinary catching up stays on foot.

Core followers whose current tile and target both lie on the trail consume its actual successive tiles. This preserves the intermediate leg of a two-tile turn instead of aiming diagonally at a later breadcrumb. Offset fans and new arrivals retain the collision-checked local routing. Client ticks interpolate one- or two-step paths over each fan's persistent 28–30 cycle duration. These small pace differences are cosmetic simulation choices. `advance` continues an unfinished click immediately after its rendered segment ends, without waiting for a GameTick. Game ticks still update destinations and retry blocked routes; per-cycle updates do not repeatedly search blocked paths. New clicks from a settled position get their own 0–24 cycle start offset. Each segment supplies its own movement heading, including the second half of a running corner. New arrivals start on one of the eight movement headings; repairs of an existing entity retain its current heading. No player/companion tracking changes facing after arrival.

Turning advances at up to 32 angle units per elapsed client cycle, with duplicate same-cycle calls doing no additional rotation. A bounded 64-cycle replay keeps sparse updates equivalent across short paths and turns without unbounded catch-up after a stall. Paths finish visually before a new plan can start from their logical endpoint; early target changes cannot cancel an in-flight step. Planning settles the previous segment and chooses its successor together, avoiding an artificial idle transition between continuous steps. Animation resources and controllers are reused, and an unchanged sequence retains its frame. Movement selects forward, sideways, or backward gait from the angular difference; a remaining movement-induced turn after stopping uses a turn-on-spot pose until aligned. Idle bodies do not acquire new look-at targets. Emotes require a stationary, aligned fan.

Weapon-name profiles cover standard movement, whips, staves and powered staves, spears/lances/halberds, crossbows, two-handed swords/godswords, scythes of vitur, elder mauls, soulreaper axes, and felling axes. These are curated pose profiles using generated cache sequence constants, with standard directional fallbacks, not a complete equipment animation database. Future or specialized weapon variants can need further profiles and still require actual-cache visual validation.

Initial arrivals model binary word-of-mouth diffusion: a spotter appears after four ticks (2.4 seconds), then waves of 2, 4, 8, 16, 32, and the remaining fans arrive roughly 16 ticks (9.6 seconds) apart. Arrivals trickle within each wave with deterministic ±2-tick reaction/pathing jitter; 30 fans are scheduled within about 45–50 seconds and 100 within about 75 seconds. Quick compresses the delays to a quarter; Instant makes new fans eligible immediately. Ordinary region loading preserves both existing fans and pending arrival deadlines. Fans enter on valid tiles 4–6 tiles away and approach on foot; geometry may require a nearer fallback. Additional fans from a size increase use the selected arrival pace. Hiding the crowd unregisters its objects and clears scene state while retaining appearances and settings; showing it starts a fresh entrance.

Overhead text renders on `OverlayLayer.UNDER_WIDGETS`, after the local player and native overheads but beneath game interfaces. Projection, viewport clipping, and label collision handling remain unchanged. This avoids the earlier `ABOVE_SCENE` pass being painted over by the local player; CPU/GPU checks in the live client remain part of the checklist below.

Equipment coverage uses the indices from `KitType` instead of a hand-written slot mapping. Head equipment does not automatically hide hair or jaw kits: only the item's explicit wear-position coverage tags do. Tests cover bare heads, open hats, hair-covering helmets, jaw-covering masks, full helmets, and torso/arm coverage.

`CrowdPopulation` treats the configured count as a hard maximum and approximate attendance target. The target may vary within `ceil(maximum * 0.20)` fans below the limit, with a minimum target of one. After 600 active game ticks, demand is sampled every 80–259 ticks using up to 40 nearby real players, the machine’s local hour, and randomness. Target attendance changes by at most one fan every 25–89 ticks. Demand reductions walk away through the same departure path as independent visits; explicit user reductions of the maximum apply immediately.

Each entity separately retains a first-spawn timestamp, recognition memory, and departure deadline. Stay lengths are `100 + min(800, exponential(mean))` ticks, with personality means of 100 for screenshotters, 140 for beggars, 200 for memers, 260 for excited fans, 350 for quiet fans, and 400 for hypemen. These are design choices, not measured player-behavior estimates. At most roughly 10% of visitors start voluntary departures concurrently. They choose collision-connected destinations beyond the gathering patch and walk there using the existing movement controller. If an exit cannot be reached, a 45-tick timeout bounds cleanup. Departing fans no longer chat, join conversations, or start idle emotes. Completed departures unregister objects and leave an 8–40 tick gap before replacement; successive replacements are staggered, receive new identities and appearances, and retain the selected entrance pace. A tiny crowd may briefly be empty. Scene rebasing preserves visit clocks and recognition; scene resets retain identity/recognition and restart entrance pacing. Shutdown clears visitors and replacement timing. No population service is queried.

Built-in first-sighting structures are explicitly marked in both short grammar and the resource corpus. They are eligible only before a fan has spoken and within 30 ticks of first spawning. Any spoken message marks the fan as having acknowledged the player. Chat reconfiguration, model repair, and scene reset do not erase that memory; a new entity starts fresh. Custom quotes remain user-authored and are not semantically filtered. Existing movement tests may hold visitors fixed to isolate scene/movement regressions; dedicated lifecycle simulations keep real timers enabled and verify replacement identities, visible walked departures, gaps, survivor objects, and cleanup.

### Research and interpretation

RuneLite's [Actor API](https://static.runelite.net/runelite-api/apidocs/net/runelite/api/Actor.html) distinguishes logical versus rendered positions, target versus current orientation, and forward/side/back/idle-turn poses. [ClientTick](https://static.runelite.net/runelite-api/apidocs/net/runelite/api/events/ClientTick.html) is a fixed 20 ms event; [GameTick](https://static.runelite.net/runelite-api/apidocs/net/runelite/api/events/GameTick.html) arrives approximately every 0.6 seconds. The diagnosed timing bug was per-call rotation plus extra planning calls, not a measured uncapped-FPS defect. The 32-unit turn limit is this simulation's chosen rate, rather than a claim that every native actor has the same rate. Sequence identifiers were checked against the locally resolved RuneLite 1.13.4 API and its [generated AnimationID source](https://github.com/runelite/runelite/blob/master/runelite-api/src/main/java/net/runelite/api/gameval/AnimationID.java).

For the pet-follow reference, the author of [Pet Pathing and Combat](https://github.com/MoukerJoe/pet-pathing-and-combat) describes a cosmetic follower tracing player turns and preserving a trailing position. That supports the ordered-path approach; its optional watch-the-player behavior is deliberately excluded here. This is a pet-inspired human follower simulation, not a reproduction of Jagex's private server-side pet logic, and humans retain walk/run locomotion.

Equipability is insufficient as a wardrobe rule. Jagex explicitly describes the [wearable coffin as a cape-slot minigame reward](https://oldschool.runescape.com/polls/2020/1610); filtering by slot alone therefore admits the exact prop reported here. The [max cape represents mastery of every skill](https://oldschool.runescape.wiki/w/Max_cape), so this wardrobe treats it as an established-account signal when choosing the rest of the outfit. That compatibility rule is a design inference, not a game restriction: a real maxed player can equip a bronze dagger.

The behavioral model follows the reported immersion problems: a visitor notices someone once, finds a nearby place to stand, talks or watches for a while, and eventually returns to their own plans. Independent clocks keep those decisions staggered. Screenshotters tend to finish sooner; regulars and hypemen tend to stay longer. Spacing, patience, arrival, departure, recognition, and outfit choices are locally simulated, with no claims of measured human behavior.
